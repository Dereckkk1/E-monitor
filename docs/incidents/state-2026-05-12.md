Documento de handoff para agentes futuros e para você mesmo amanhã.
Captura o estado em que o sistema ficou após a sequência de incidentes
do dia 9-12 e o que precisa acontecer pra finalizar a recuperação.

## TL;DR

Aconteceram **3 incidentes correlatos** entre 9 e 12 de maio:

1. **Falso-positivo** de AMBIENTAL JINGLE em 101 FM (9/5)
2. **Falso-negativo** + **retração indevida** em Oeste Capital (11/5)
3. **Quase-perda do pgdata** ao tentar deployar o fix do #2 (12/5) —
   na verdade dado sobreviveu o tempo todo em
   `/mnt/db/pgdata` (bind mount via override file gitignored). Operamos
   por ~4h achando que tudo tinha sumido porque comandos manuais não
   usavam o override.

A causa raiz comum dos #1 e #2 (compartilhamento de áudio entre
comerciais) levou a 3 iterações do algoritmo `shared-hash` (F-108
v1→v2→v3). Durante a "fake recovery" do #3 implementamos várias
camadas de defesa em profundidade que agora são redundantes — boa
redundância, dado que o estado original era invisível pra quem não
sabia do override file.

**Sistema voltou com dado original intacto** quando o usuário rodou
`deploy.sh` (que inclui o override). Recadastro feito durante a
fake-recovery está orfão num named volume `docker_pgdata` (provavelmente
descartável). **Defesas implementadas:** bind mount agora explícito
no base yml via env vars, R2 backup funcional, snapshot GCP diário,
alerta Prometheus de backup ausente, regras em CLAUDE.md sobre
`--no-deps` e override file.

### Notas sobre o override file

`infra/docker/docker-compose.override.yml` na VM contém:

```yaml
services:
  postgres:
    volumes:
      - /mnt/db/pgdata:/var/lib/postgresql/data
      - /mnt/db/pg_archive:/var/lib/postgresql/archive
  minio:
    volumes:
      - /mnt/data/minio:/data
  api:
    volumes:
      - /mnt/data/masters:/app/masters
      - /mnt/data/audio-refs:/app/audio-refs
```

Está gitignored. **`deploy.sh` sempre inclui esse arquivo no comando.**
Comandos manuais (incluindo qualquer coisa que um agente futuro rodar
em diagnóstico) precisam incluir `-f docker-compose.override.yml`
explicitamente ou cair em armadilha. Ver `CLAUDE.md` §4.7.

Após o merge de fix/postgres-bind-mount em master, o **base yml já
suporta bind mount via env vars** (PGDATA_HOST_PATH etc). Em uma
limpeza futura, vale migrar a config do override para o `.env` e
deletar o override file — single source of truth.

   O script faz git pull, build, up, espera migrations, valida health.

2. **(Opcional) Setar `RADIOCHECK_ENV=production` no `.env` da VM**
   pra que os spans OTel saiam com o `deployment.environment` correto.

3. **(Opcional) Migrar override file pra base yml**: em vez de
   manter o `docker-compose.override.yml` na VM, adicionar no
   `.env`:
   ```
   PGDATA_HOST_PATH=/mnt/db/pgdata
   MINIODATA_HOST_PATH=/mnt/data/minio
   MASTERSDATA_HOST_PATH=/mnt/data/masters
   ```
   Funciona idêntico, mas explícito e versionável. Depois pode
   deletar o override file.

4. **Recadastro feito durante a fake-recovery**: ficou orfão no
   named volume `docker_pgdata` (não montado mais por ninguém).
   Provavelmente irrelevante — usuário relatou que tinha cadastrado
   pouco. Se quiser recuperar: subir um postgres efêmero apontado
   nesse volume, `pg_dump`, comparar com o dado real em
   `/mnt/db/pgdata`. Esforço >>> benefício na maioria dos casos.

```bash
           ROUND(100.0 * COUNT(*) FILTER (WHERE fh.is_shared) / NULLIF(COUNT(*),0), 1) shared_pct
```

## Quando você acordar amanhã

Ordem mental:

1. ✅ Sistema está respondendo? `curl https://api.e-monitor.online/v1/internal/health`
2. ✅ Backup rodou na noite? Confere R2 listagem (deve ter ≥ 2 arquivos)
3. ✅ Snapshot GCP rodou? GCP Console → Snapshots
4. Termina o recadastro do catálogo
5. Roda script de migração de volumes (bind mount)
6. Deploya o F-108 v3
7. Olha o Grafana / Prometheus por uma manhã pra ver se nada está
   anômalo

Depois disso fecha PRs das branches em ordem e segue a vida.
