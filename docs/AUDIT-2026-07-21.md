**Data:** 2026-07-21
**Escopo:** Backend Go (`workers/`), frontend React (`frontend/`), infraestrutura Docker (`infra/docker/`), dependências (Go modules + npm).

## Sumário Executivo

O **núcleo de segurança da aplicação é sólido**: a superfície de injeção está bem defendida (pgx parametrizado, whitelist de ordenação, `html/template` nos e-mails, sem sinks XSS no React), o JWT bloqueia `alg:none`/algorithm-confusion, a entrega de webhooks é um modelo de referência anti-SSRF, e o isolamento de tenant *interno* (viewer via JWT) é consistente com padrão anti-oracle.

O risco concentra-se em **duas categorias**: (1) uma falha de autorização crítica na API externa de clientes, e (2) a postura de **infraestrutura/segredos**, onde credenciais de produção estão em texto puro e serviços de dados ficam expostos com credenciais triviais.

**Contagem:** 2 Críticos · 8 Altos · 16 Médios · 8 Baixos.

### Top 5 — corrigir primeiro
1. **[C-01] BOLA total na API externa `/v1/detections`** — a chave de API de um cliente lê os dados de **todos** os clientes.
2. **[C-02] Segredos de produção em cleartext** no `.env` (JWT_SECRET, senha do admin, App Password do Gmail, Postgres/MinIO triviais) — rotacionar já.
3. **[H-01] Datastores expostos em `0.0.0.0`** (Postgres com senha `radiocheck`, Redis/NATS sem auth, MinIO).
4. **[H-04] Zero rate-limiting** — login aberto a brute force / credential stuffing.
5. **[H-03] `/metrics` público** no servidor exposto pelo Cloudflare Tunnel.

## CRÍTICOS

### [C-01] BOLA cross-tenant na API externa `/v1/detections` — escopo da API key é descartado
- **✅ CORRIGIDO (2026-07-21):** novo middleware `auth.APIKeyViewerScope` (`workers/internal/auth/apikey.go`) converte o `client_id` da API key em claims sintéticas de viewer (fail-closed: 401 se sem client_id válido), montado no grupo `/v1` logo após `APIKey.Middleware` (`router.go`). Reusa o caminho de enforcement já testado (`ClientScopeFromContext`). Cobertura: `apikey_scope_test.go` (scope correto + 2 casos fail-closed). Validado ao vivo: `/v1/detections` sem key → 401.
- **Arquivos:** `workers/internal/api/router.go:101-112`; `workers/internal/auth/apikey.go:45-49,81`; `workers/internal/auth/scope.go:26-43`; `workers/internal/api/handlers/detections.go:41,163,251`; `workers/internal/catalog/detections.go` (filtro `client_id`).
- **Classe:** OWASP API1:2023 (BOLA) / A01:2021 / CWE-639, CWE-284.
- **Confiança:** **CONFIRMADO** (verificado manualmente, cadeia completa).
- **Descrição:** As rotas externas (`GET /v1/detections`, `/v1/detections/{id}`, `/v1/detections/{id}/evidence`) são protegidas por `APIKeyMiddleware`, que resolve o `client_id` da chave e o grava no contexto sob `clientIDKey`. Porém `ClientIDFromContext` — o único leitor dessa chave — **nunca é chamado por nenhum handler** (grep confirma: só a definição e o setter existem). Os handlers reutilizam a lógica interna, que resolve o tenant via `ClientScopeFromContext` — função que lê os *claims do JWT*. Como uma requisição por API key **não tem JWT**, ela retorna `nil`, e a convenção do sistema é `nil = "sem escopo" = vê tudo`. Resultado:
  - `List`: `f.ClientID = nil` → o filtro SQL não restringe → retorna detecções de todos os clientes.
  - `Get`/`Evidence`: o bloco `if scope != nil { …verifica dono… }` é **pulado** → qualquer `detection_id` e qualquer áudio de evidência são servidos.
- **Cenário de ataque:** Cliente A cria uma API key legítima. Com ela:
  ```
  curl -H "X-Api-Key: <chave_de_A>" https://api/v1/detections
  # → 200 com veiculações de TODOS os clientes (station, material, campaign_id, evidence_key…)
  curl -H "X-Api-Key: <chave_de_A>" https://api/v1/detections/<id_de_B>/evidence
  # → 200 com o áudio de evidência da campanha do cliente B
  ```
  Vaza grade de mídia, materiais e gravações de concorrentes — exatamente o que a segmentação por API key deveria isolar (§13.1).
- **Remediação:**
  1. Fazer os handlers externos resolverem o tenant a partir de `auth.ClientIDFromContext` (o `client_id` da chave), aplicando-o ao `ListFilter.ClientID` e ao check de posse em `Get`/`Evidence`. Preferir um wrapper/adaptador externo que **force** o `client_id` da chave em vez de reusar o handler interno cru.
  2. Defense-in-depth: para a superfície `/v1`, tratar "sem escopo resolvível" como **negar**, não "ver tudo".
  3. Adicionar teste de authz cross-tenant (dois clientes, cada um só vê o próprio).

### [C-02] Segredos de produção em cleartext no `.env`, com credenciais triviais de DB/MinIO
- **Arquivos:** `infra/docker/.env` (JWT_SECRET, admin password, SMTP_PASS, POSTGRES_PASSWORD, MINIO_ROOT_*), `infra/docker/docker-compose.yml:74-76,182-183,266,371`.
- **Classe:** CWE-798 (credenciais hardcoded) / CWE-312 (cleartext storage) / CWE-1392 (credencial default) / CIS Docker 5.x.
- **Confiança:** **CONFIRMADO** (arquivo lido).
- **Descrição:** O `.env` contém segredos vivos em texto puro:
  - `JWT_SECRET` — assina **todas** as sessões; vazado, permite forjar qualquer token admin sem senha.
  - `RADIOCHECK_BOOTSTRAP_ADMIN_PASSWORD` — senha do admin `tatico3@hubradios.com` (valor mascarado: `!!Der…05`).
  - `SMTP_PASS` — App Password viva do Gmail Workspace (mascarado: `fqem…obo`).
  - `POSTGRES_PASSWORD=radiocheck` e `MINIO_ROOT_USER/PASSWORD=minioadmin/minioadmin` — credenciais triviais/default.
  - `GF_SECURITY_ADMIN_PASSWORD=admin` (Grafana) — ver H-02.
  Segredos passados como `environment:` no compose também ficam visíveis em `docker inspect` e no ambiente de todo processo do container.
- **Impacto:** Qualquer leitura de disco (dev ou VM) ou de `docker inspect` entrega controle total: forjar sessões admin, ler e-mail, dump do banco, controle do object storage.
- **Remediação:**
  1. **Rotacionar imediatamente** os 5 segredos (JWT, senha admin, App Password Gmail, Postgres, MinIO, Grafana).
  2. Migrar para **Docker secrets** (`secrets:` + variantes `_FILE`).
  3. Trocar `POSTGRES_PASSWORD`/`MINIO_ROOT_*`/Grafana por valores fortes e distintos do `.env.example`.
  4. Nunca reusar App Password de Gmail como segredo de app.
- **Nota positiva:** os segredos **nunca foram commitados** — `.gitignore` cobre `.env*` e `git log --all --diff-filter=A` não mostra `.env`. O risco é de disco/runtime, não de histórico público.

## ALTOS

### [H-01] Portas de datastore/observabilidade bindadas em `0.0.0.0`
- **Arquivo:** `docker-compose.yml:91` (PG 5432), `:101` (Redis 6379), `:112-113` (NATS 4222/8222), `:144-145` (MinIO 9000/9001), `:361` (Prometheus), `:369` (Grafana), `:383` (Alertmanager), `:394-397` (Jaeger), `:352` (node-exporter).
- **Classe:** CIS Docker 5.7 / CWE-668.
- **Confiança:** CONFIRMADO no compose base; **POTENCIAL** para exposição à internet (depende do firewall GCP e do `docker-compose.override.yml` gitignored da VM).
- **Descrição:** O padrão `"${PORT}:5432"` faz bind em `0.0.0.0`. Combinado com C-02 (Postgres senha `radiocheck`, Redis/NATS sem auth), qualquer host que alcance a VM tem acesso direto ao banco, ao storage e aos painéis. **Docker publica portas via iptables contornando o `ufw`** — "ufw deny" não basta.
- **Remediação:** Bindar em loopback (`"127.0.0.1:${PORT}:…"`) todo serviço que só precisa ser acessado pela própria VM; serviços entre containers dispensam `ports:`. Confirmar regras de firewall GCP na camada de rede.

### [H-02] Grafana com credencial default `admin/admin` e porta publicada
- **Arquivo:** `docker-compose.yml:371` + `:369`.
- **Classe:** CWE-798 / CWE-1392.
- **Confiança:** CONFIRMADO.
- **Remediação:** senha via Docker secret, bind em loopback, `GF_AUTH_ANONYMOUS_ENABLED=false` explícito.

### [H-03] `/metrics` público sem auth no servidor exposto pelo Cloudflare Tunnel
- **Arquivo:** `workers/internal/api/router.go:115` (comentário confirma "public, no auth"); skip explícito no blocklist (`reqmetrics/middleware.go:112`, `blocked.go:128`).
- **Classe:** CWE-200.
- **Confiança:** CONFIRMADO (no-auth); POTENCIAL para exposição externa (depende do ingress do Tunnel).
- **Descrição:** `/metrics` está montado no servidor HTTP principal (8080), exatamente o que o Tunnel expõe em `e-monitor.online`. Responde inclusive a IPs bloqueados. Provavelmente entrega toda a telemetria Prometheus (rotas internas, cardinalidade de emissoras/campanhas) a qualquer um na internet.
- **Remediação:** servir `/metrics` num listener interno separado (como já se faz com pprof em `127.0.0.1:6060`), ou proteger com auth/allowlist, ou bloquear o path na config do Tunnel.

### [H-04] Ausência total de rate-limiting / anti-brute-force
- **✅ PARCIALMENTE CORRIGIDO (2026-07-21):** `auth.LoginRateLimiter` (`workers/internal/auth/ratelimit.go`, janela fixa por IP, 10/min) montado na rota de login (`router.go`), respondendo 429 + `Retry-After: 60`. Cobertura: `ratelimit_test.go` (4 testes). Validado ao vivo: 11ª tentativa → 429. **Pendente:** throttle nos endpoints caros (`/insights`, `/reports/*`, `/detections/export`, uploads) e lockout progressivo por conta.
- **Arquivo:** `workers/internal/api/router.go:74-98` (cadeia de middlewares); `workers/internal/api/handlers/auth.go:47` (`Login`, rota pública em `router.go:121`).
- **Classe:** OWASP A07 / CWE-307 / CWE-770.
- **Confiança:** CONFIRMADO (varredura por `rate|limiter|throttle|429` → nenhum middleware de throttle; a `reqmetrics.BlockList` é bloqueio **manual** de IP pelo admin).
- **Descrição:** `/v1/internal/auth/login` é público e chama bcrypt sem contador de tentativas por IP/conta. O mesmo vale para endpoints caros (`/insights`, `/reports/*`, `/detections/export`, uploads). O pool do Postgres é pequeno, tornando DoS de aplicação barato.
- **Remediação:** rate-limit por IP no login (ex. 5/min) + lockout progressivo por conta; throttle por usuário nos endpoints caros, com `429 + Retry-After`. Reusar o padrão `checkRate` de `apikey.go`.

## MÉDIOS

### [M-01] Port-scanner cego da rede interna via `connection-test` + `Ping`
- **Arquivo:** `workers/internal/probe/probe.go:59-83` (`hostPort` valida só esquema), `probe/ffmpeg.go:19-32` (`Ping`, dial TCP cru), `api/handlers/stations.go:190-255` (`ConnectionTest`).
- **Classe:** OWASP A10 SSRF / CWE-918. **Confiança:** CONFIRMADO (oráculo booleano + timing).
- **Descrição:** `hostPort()` rejeita `file://`/`gopher://` mas aceita qualquer host (`127.0.0.1`, `10.x`, `169.254.169.254`). `Ping` retorna `latency_ms`/`status` no JSON → scanner de portas interno pronto. Gated a `admin`/`operator`, então é SSRF que cruza a fronteira **operador → infra interna**, não anônimo.
- **Cenário:** `POST /v1/internal/stations/{id}/connection-test` com `{"tests":["ping"],"url":"http://postgres:5432"}` (ou `redis:6379`, `clap-verifier:8080`, faixas `10.x`) — a resposta revela quais serviços internos estão vivos e em quais portas. *Roubo de credencial via metadata GCP é improvável (exige header `Metadata-Flavor`); o impacto real é reconhecimento de rede.*
- **Remediação:** aplicar na trilha de probe a **mesma** defesa de `webhook/safehttp.go` — resolver o host, rejeitar espaço privado/loopback/link-local (`isPrivateIP`) e discar o IP validado (fecha DNS-rebinding). Idealmente reusar um `safeDialer` compartilhado.

### [M-02] SSRF cego via ffmpeg/ffprobe do ingestor
- **Arquivo:** `workers/internal/ingestor/ffmpeg.go:36-48,153-227`, `ingestor/worker.go:236`.
- **Classe:** OWASP A10 / CWE-918. **Confiança:** CONFIRMADO (alcançabilidade; cego).
- **Descrição:** `stream_url` vai direto a `ffmpeg -i`/`ffprobe -i` sem filtro de IP. Um `stream_url` interno (`http://minio:9000`, `http://10.0.0.x`) faz o worker permanente bater lá com reconnect (oráculo de alcançabilidade + DoS/pivot).
- **Remediação:** validar `stream_url` (resolver + bloquear IP privado) no ponto de persistência e antes de spawnar ffmpeg; ou rodar workers de ingest numa egress network restrita. Passar `-protocol_whitelist file,crypto,http,https,tcp,tls` ao ffmpeg.

### [M-03] `Create`/`Update` de station não validam esquema do `stream_url`
- **Arquivo:** `workers/internal/api/handlers/stations.go:58-77,98-127` (só exigem `!= ""`); contraste com `validStreamScheme` em `:280-283`, aplicado só em `UpdateStreamURL`.
- **Classe:** CWE-918 (protocol handlers). **Confiança:** CONFIRMADO (gap).
- **Descrição:** por `Create`/`Update` persiste-se `stream_url = file:///etc/passwd`, `concat:…`, `gopher://…`; o ingestor entrega ao ffmpeg, que suporta esses handlers (leitura de arquivo local).
- **Remediação:** aplicar `validStreamScheme` (ou o validador SSRF completo) em `Create`/`Update` também. Preferir `url.Parse` + `strings.EqualFold` (o atual `raw[:7]=="http://"` é case-sensitive).

### [M-04] Nenhum header de segurança HTTP (backend nem SPA)
- **Arquivo:** `workers/internal/api/router.go:577-588` (único middleware de resposta, só CORS); sem `_headers` no `frontend/`.
- **Classe:** OWASP A05 / CWE-1021 / CWE-693. **Confiança:** CONFIRMADO (busca por HSTS/CSP/X-Frame-Options/nosniff no app → zero).
- **Descrição:** sem `X-Frame-Options`/CSP `frame-ancestors` (clickjacking), sem CSP (um XSS na SPA roda sem mitigação e — com o JWT em sessionStorage, L-04 — exfiltra o token), sem HSTS (SSL-strip), sem `nosniff`.
- **Remediação:** middleware no backend com `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security`. Para a SPA, `_headers` no Cloudflare Pages com CSP (`default-src 'self'`, `frame-ancestors 'none'`).

### [M-05] CORS `Access-Control-Allow-Origin: *`
- **Arquivo:** `workers/internal/api/router.go:579-581`.
- **Classe:** OWASP A05 / CWE-942. **Confiança:** CONFIRMADO.
- **Descrição:** wildcard incondicional para toda origem, inclusive `/v1/internal/*`. **Atenuado** porque a auth é Bearer (sem cookies) e não há `Allow-Credentials: true` — o browser não anexa o token cross-site. É desvio de hardening, não roubo de sessão clássico.
- **Remediação:** allowlist explícita de origens (domínio do painel), match exato. Manter sem `Allow-Credentials` enquanto o auth for Bearer.

### [M-06] Upload sem `MaxBytesReader` em `/materials` e `/commercials` → disco cheio (DoS)
- **Arquivo:** `workers/internal/api/handlers/materials.go:86` (`ParseMultipartForm(64<<20)`), `commercials.go:71` (`50<<20`).
- **Classe:** OWASP A05 / CWE-770. **Confiança:** CONFIRMADO.
- **Descrição:** o argumento de `ParseMultipartForm` é só o `maxMemory` — partes maiores **derramam para arquivos temporários sem teto**. Os handlers novos fazem certo (`detections.go:394`, `detections_manual_batch.go:74`, `suggestions.go:388` usam `MaxBytesReader`); materials/commercials ficaram para trás. Dado o histórico de disco cheio na VM, é concreto (requer role admin/operator).
- **Remediação:** `r.Body = http.MaxBytesReader(w, r.Body, <teto>)` antes de `ParseMultipartForm`.

### [M-07] Containers rodam como root
- **Arquivo:** `workers.Dockerfile:19-38` e `fingerprint.Dockerfile:1-10` (sem `USER`); sem `user:` no compose (só `clap-verifier` tem `USER appuser`).
- **Classe:** CIS Docker 4.1/5.x / CWE-250 / MITRE T1611. **Confiança:** CONFIRMADO.

- **Remediação:** `USER 65532:65532` nos Dockerfiles; por serviço `security_opt: ["no-new-privileges:true"]`, `cap_drop: [ALL]`, `read_only: true` + `tmpfs`.

- **Arquivo:** `workers/internal/api/handlers/auth.go:65-105`.
- **Classe:** OWASP A07 / CWE-204 + CWE-208. **Confiança:** CONFIRMADO.
- **Descrição:** (1) usuário inexistente → 401 `invalid credentials`; usuário desativado → 403 `account_disabled`; cliente suspenso → 403 `client_disabled` — os 403 confirmam existência. (2) usuário inexistente retorna **sem** executar bcrypt → diferença de timing é oráculo. Potencializa H-04.
- **Remediação:** unificar resposta de falha de credencial; executar bcrypt "dummy" quando o usuário não existe para nivelar o tempo; fazer o gating de conta/cliente após validar a senha.

### [M-14] `X-Forwarded-For` confiado cegamente (`middleware.RealIP`)
- **Arquivo:** `workers/internal/api/router.go:75`; `reqmetrics/middleware.go:122-139`; `reqmetrics/blocked.go`.
- **Classe:** OWASP A05 / CWE-290 + CWE-348. **Confiança:** POTENCIAL.
- **Descrição:** `RealIP` reescreve `RemoteAddr` a partir do XFF sem validar proxy confiável. Um atacante spoofa XFF para evadir ban de IP ou poluir o painel `/admin/monitoring`. **Mitigado se** o Cloudflare Tunnel sobrescrever o XFF de entrada — não verificável no código.
- **Remediação:** allowlist de proxies confiáveis; processar o XFF da direita p/ esquerda parando no primeiro hop confiável.

### [M-15] Sem resource limits/`pids_limit`/healthchecks em vários serviços
- **Arquivo:** `docker-compose.yml` — `redis`, `nats`, `prometheus`, `grafana`, `alertmanager`, `jaeger`, `fingerprint` sem `mem_limit`/`pids_limit`; vários sem healthcheck.
- **Classe:** CIS Docker 5.10/5.11 / CWE-400. **Confiança:** CONFIRMADO.
- **Descrição:** sem `pids-limit`, um fork bomb num container não é contido. (`api` sem `mem_limit` é decisão documentada — os ~200 ffmpeg dominam o RSS.)
- **Remediação:** `pids_limit`, `mem_limit`, `cpus` por serviço.

### [M-16] Advisories moderados no frontend (dompurify / react-router / vite)
- **Arquivo:** `frontend/package.json` + transitivas. **Confiança:** CONFIRMADO (npm audit).
- **Descrição:**
  - `dompurify 3.4.6` (via `jspdf 4.2.1`) — XSS/prototype pollution; contido (só exercido na geração de PDF a partir de conteúdo interno).
  - `react-router-dom 6.30.3` — GHSA-2j2x-hqr9-3h42 (open redirect via path `//`).
  - `vite 8.0.14` — GHSA-fx2h-pf6j-xcff / GHSA-v6wh-96g9-6wx3 (**dev-only**, não afeta o bundle de prod).
- **Remediação:** `jspdf`→dompurify ≥3.4.11, `react-router` 6.30.4+, `vite` ≥8.0.16 (dev, baixa urgência). Tudo via procedimento 5.3.

## BAIXOS

### [L-01] IDOR cross-tenant entre operadores em API keys/webhooks
- **Arquivo:** `workers/internal/api/handlers/apikeys.go:17,49,64`; `router.go:274-295`.
- **Classe:** OWASP API1 / CWE-639. **Confiança:** CONFIRMADO.
- **Descrição:** `List/Create/Revoke` de API keys usam `clientID` do path sem cruzar com o escopo do chamador. Gated a `admin`/`operator` (não atingível por viewer) — é **por design** (staff interno, "until tenancy is implemented"), mas concentra risco se uma conta de operador for comprometida.
- **Remediação:** ao implementar tenancy, cruzar `clientID` do path com o escopo do ator; enquanto isso, restringir mutações sensíveis a `admin` e auditar.

### [L-02] bcrypt cost 10
- **Arquivo:** `bootstrap.go:75`, `users.go:178,329`, `me.go:127`. **Classe:** CWE-916. **Confiança:** CONFIRMADO.
- **Remediação:** elevar para 12 (rehash transparente no próximo login). bcrypt trunca em 72 bytes — rejeitar/normalizar senhas maiores.

### [L-03] `crypto/rand.Read` com erro ignorado na geração de API key
- **Arquivo:** `workers/internal/auth/apikey.go:19` (`rand.Read(raw) //nolint:errcheck`). **Classe:** CWE-703/CWE-330. **Confiança:** CONFIRMADO.
- **Descrição:** falha/leitura parcial produziria chave previsível sem sinal. Probabilidade baixíssima no Linux; higiene.
- **Remediação:** tratar o erro e propagar falha em vez de emitir chave fraca.

### [L-04] JWT em `sessionStorage` (exfiltrável por XSS)
- **Arquivo:** `frontend/src/contexts/AuthContext.jsx:21-27`; `frontend/src/api/client.js:13-20`. **Classe:** OWASP A07 / CWE-522. **Confiança:** CONFIRMADO.
- **Descrição:** token de 8h acessível a qualquer JS. Com a ausência de CSP (M-04), um XSS lê e exfiltra o token → sequestro de sessão por 8h. O próprio código tem TODO reconhecendo.
- **Remediação:** migrar para cookie `HttpOnly; Secure; SameSite=Strict` + refresh token; no mínimo CSP estrita e TTL menor.

### [L-05] CSV formula injection nos relatórios
- **Arquivo:** `workers/internal/api/handlers/reports.go:209-230`. **Classe:** CWE-1236. **Confiança:** POTENCIAL.
- **Descrição:** `MaterialTitle`/`StationName` escritos direto no CSV; um material nomeado `=HYPERLINK("http://evil","x")` executa ao abrir no Excel/LibreOffice.
- **Remediação:** prefixar com `'` campos de texto que comecem com `= + - @ \t \r`.

### [L-06] Postgres `sslmode=disable` em todas as conexões
- **Arquivo:** `docker-compose.yml:128,172,314,439`. **Classe:** CWE-319. **Confiança:** CONFIRMADO.
- **Remediação:** reduzir superfície (bind loopback de 5432); TLS no PG (`sslmode=require`) para tráfego cross-host.

### [L-07] App usa credenciais ROOT do MinIO
- **Arquivo:** `docker-compose.yml:182-183`. **Classe:** CWE-250/269. **Confiança:** CONFIRMADO.
- **Descrição:** comprometer a API entrega controle total do storage, não só o bucket de evidências.
- **Remediação:** usuário/policy MinIO escopado ao bucket `radiocheck-evidence` (get/put/list).

### [L-08] `apk add` em runtime no entrypoint (backup, radio-sim)
- **Arquivo:** `docker-compose.yml:463` (backup: `apk add aws-cli`), `:297` (radio-sim: `apk add ffmpeg`). **Classe:** CIS Docker 4.x / MITRE T1195. **Confiança:** CONFIRMADO.
- **Descrição:** o container de backup instala `aws-cli` a cada start — mirror indisponível/comprometido quebra o backup (o controle que já falhou em 2026-05-12).
- **Remediação:** imagem de backup dedicada (multi-stage) com aws-cli embutido e versionado.

## O que está BEM-FEITO (não regredir)

- **Injeção:** nenhuma SQLi/XSS/SSTI encontrada. pgx com placeholders `$1` consistente; `sort`/`status`/`order` sempre whitelisted; SQL dinâmico só com constantes internas; `html/template` (auto-escaping) nos e-mails via `//go:embed`; React sem `dangerouslySetInnerHTML`/`innerHTML`.
- **Webhooks (SSRF):** `webhook/safehttp.go` é modelo de referência — bloqueia privado/loopback/link-local/multicast/`169.254.169.254`, disca o IP resolvido (anti-DNS-rebinding), revalida redirect, exige HTTPS em prod, cap de 4KB + timeout 10s. **Replicar essa lógica nas trilhas de stream/probe (M-01/M-02).**
- **JWT:** HS256 fixado com guarda explícita contra `alg:none` e algorithm-confusion; segredo ≥32 bytes de env; sem uso de `kid`/`jku`.
- **Mass assignment:** `me.Patch` usa DTO só com `name`/`phone`; `users.Patch/Create` são admin-only com allowlist de `role`/`client_id`. Sem auto-promoção.
- **Excessive data exposure:** `PasswordHash` tem `json:"-"`; webhook secret mascarado no DTO; `dev_notes` de sugestões removido para não-dev.
- **Isolamento de tenant interno (viewer):** scope-check por `ClientScopeFromContext` com 404 anti-oracle; `ClientScopeFromContext` é fail-closed (viewer sem client_id → `uuid.Nil`, não acesso total).
- **golang-jwt/jwt/v5 v5.3.1** — acima dos fixes de CVE-2025-30204 e CVE-2024-51744. `pgx`, `chi`, `nats.go` sem CVE conhecido. `x/crypto` com advisories mas nenhum alcançável.
- **Dependency confusion:** risco desprezível (sem pacotes privados internos, tudo em `registry.npmjs.org`). Lockfile não podado (`@emnapi` presente, regra 5.4 OK).
- **`deploy.sh`:** robusto — backup pré-deploy verificado, tripwire de row-count, shadow migration test, guard de branch, sem `--force-recreate`, sem vazamento de segredo em log.
- **pprof:** corretamente em `127.0.0.1:6060`, não publicado.

### ⚠️ Verificação operacional necessária (não-código)
- **`RADIOCHECK_ENV`** controla `allowPrivate`/`AllowInsecureURL` na defesa SSRF do webhook (`safehttp.go:216-219`). Se prod estiver como `development`/`dev`, **toda a defesa SSRF do webhook é desligada** e http:// plaintext é aceito. **Confirmar que a VM de prod tem `RADIOCHECK_ENV=production`.**
- **Firewall GCP:** confirmar que as portas de datastore/observabilidade (H-01) não estão abertas na internet na camada de rede (Docker contorna `ufw`).
